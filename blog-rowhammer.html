Rowhammer — Flipping Bits From Userspace

2026-05-30·~10 MIN READ·CLEARANCE: DANGER
DRAMHardwareExploit Priv-EscSide-ChannelPhysics

Your hardware is lying to you. Every DRAM chip in your machine stores bits as charge in microscopic capacitors. And those capacitors leak. If you read one memory row fast enough, the electrical interference flips bits in adjacent rows — rows you don't own, can't access, and aren't supposed to touch. This is Rowhammer: a software exploit that attacks physics itself.

[!] ADVISORY

This transmission documents attack techniques for educational purposes. These methods can compromise system integrity. Do not use against systems you do not own.

00 // THE PHYSICS OF DRAM

A DRAM cell is the simplest possible storage: one transistor and one capacitor. The capacitor holds charge (bit = 1) or doesn't (bit = 0). The transistor gates access during reads and writes. That's it.

The problem: capacitors discharge. Every DRAM cell loses charge over time, which is why DRAM needs periodic refresh — every 64ms, the memory controller reads and rewrites every row to restore charge levels. Between refreshes, bits are vulnerable.

Modern DRAM cells are fabricated at process nodes below 20nm. At these scales, the capacitors are packed so tightly that electromagnetic coupling between adjacent cells is no longer negligible. When you activate (read) a row, the voltage spike on the wordline disturbs capacitors in neighboring rows — a phenomenon called cell-to-cell interference or disturbance error.

The Critical Geometry

DRAM is organized in a 2D grid: 

        Column 0   Column 1   Column 2   ...   Column N
Row 0   [cell]     [cell]     [cell]     ...   [cell]
Row 1   [cell]     [cell]     [cell]     ...   [cell]     ← VICTIM
Row 2   [cell]     [cell]     [cell]     ...   [cell]
Row 3   [cell]     [cell]     [cell]     ...   [cell]
...

When you repeatedly activate Row 0 and Row 2 (the aggressors), the electrical disturbance accumulates in Row 1 (the victim). If this happens faster than the refresh cycle can restore the charge, bits flip.

DRAM Rowhammer — Double-Sided Attack
Aggressor rows hammer · Victim bits flip in real-time

01 // THE ATTACK: DOUBLE-SIDED ROWHAMMER

The basic attack is stupidly simple. You need two memory accesses to aggressor rows, executed as fast as possible, bypassing the CPU cache: 

// The essence of Rowhammer in x86 assembly
loop:
    mov     (aggressor_row_1), %rax     // Read row A
    mov     (aggressor_row_2), %rbx     // Read row B
    clflush (aggressor_row_1)            // Flush from cache
    clflush (aggressor_row_2)            // Flush from cache
    mfence                               // Memory barrier
    jmp     loop                         // Repeat ~millions of times

The clflush instruction is critical — without it, reads hit the CPU cache and never reach DRAM. By flushing after each read, we force every iteration to hammer the actual DRAM cells.

Double-sided Rowhammer (hammering rows on both sides of the victim) is dramatically more effective than single-sided, because the victim row receives disturbance from both directions simultaneously.

How Many Activations?

The number of row activations needed to induce a flip depends on the DRAM technology: 

TECHNOLOGY      ACTIVATIONS TO FLIP     YEAR
────────────────────────────────────────────
DDR3            ~140,000                2014
DDR4            ~40,000-80,000          2016-2020
DDR4 (20nm)     ~10,000                 2020+
LPDDR4          ~5,000-20,000           2020+
DDR5            ~4,800 (TRRespass)      2024

The trend is clear: as geometry shrinks, fewer activations are needed. The attack is getting easier, not harder.

02 // WHY THIS IS TERRIFYING

Rowhammer breaks the fundamental abstraction that software operates on: memory isolation. Every security mechanism in your OS — process isolation, virtual memory, user/kernel separation, sandboxing — assumes that one process cannot modify another process's memory. Rowhammer violates this assumption at the hardware level.

THE CORE INSIGHT

Rowhammer is not a software bug. It is not a configuration error. It is a fundamental property of DRAM physics that cannot be fully patched in software. Every mitigation is a workaround, not a fix.

03 // REAL EXPLOITS

Google Project Zero — NaCl Sandbox Escape (2015)

The seminal exploit. Google's Mark Seaborn and Thomas Dullien demonstrated Rowhammer as a practical security threat by escaping the Native Client (NaCl) sandbox on x86 Linux. The attack:

  1. The attacker runs a NaCl module (sandboxed, unprivileged code)
  2. The module performs double-sided Rowhammer using clflush
  3. Bit flips in page table entries (PTEs) change physical page mappings
  4. The attacker gains read/write access to arbitrary physical memory
  5. Kernel code injection → full root access

Total time to root: under 1 hour on a vulnerable machine.

Rowhammer.js — Browser-Based Attack (2015)

Researchers at TU Graz demonstrated Rowhammer from JavaScript — no native code needed. By exploiting large typed arrays and cache eviction patterns (since clflush isn't available in JS), they could induce bit flips from a web page. Your browser tab can flip bits in kernel memory. Let that sink in.

Drammer — Android Privilege Escalation (2016)

VUSec demonstrated Drammer: a deterministic Rowhammer attack on ARM devices (Android phones). The key innovation: using the Android ION memory allocator to obtain physically contiguous memory, enabling precise double-sided hammering without knowledge of DRAM address mapping. Root achieved on multiple Samsung Galaxy and Nexus devices.

RAMBleed — Reading Memory via Rowhammer (2019)

A twist: instead of flipping bits to corrupt data, RAMBleed reads bits by observing which bits flip. The data-dependent nature of Rowhammer (a cell's susceptibility depends on the charge of neighboring cells) becomes a side channel. The attacker can extract OpenSSH private keys by analyzing flip patterns.

TRRespass — Bypassing DDR4 Mitigations (2020)

DDR4 introduced Target Row Refresh (TRR) as a mitigation — the memory controller tracks frequently activated rows and preemptively refreshes their neighbors. TRRespass showed that TRR can be bypassed using carefully crafted many-sided hammering patterns that confuse the tracking mechanism. Out of 42 DDR4 DIMMs tested, all were vulnerable.

04 // THE PHYSICS: WHY MITIGATION IS HARD

The fundamental problem is the capacitor coupling coefficient. When an aggressor row's wordline is activated, the voltage transient couples capacitively to victim cells:

$$\Delta V_{\text{victim}} = C_{\text{coupling}} \cdot \frac{\Delta V_{\text{wordline}}}{C_{\text{cell}} + C_{\text{coupling}}}$$

As cell geometry shrinks:

  • \(C_{\text{cell}}\) decreases (smaller capacitor = less stored charge)
  • \(C_{\text{coupling}}\) increases (cells packed closer = more electromagnetic interference)
  • The ratio \(C_{\text{coupling}} / C_{\text{cell}}\) grows — flips become easier

This is a scaling law. Every DRAM shrink makes Rowhammer worse. There is no Moore's Law rescue here — the physics works against you.

05 // MITIGATIONS AND WHY THEY FAIL

Target Row Refresh (TRR)

The memory controller tracks "hot" rows and refreshes neighbors. Problems:

  • Tracking is approximate — limited counter space means eviction-based bypass
  • Many-sided patterns (TRRespass) exceed the tracker's capacity
  • Implementation is vendor-specific and often proprietary (can't audit)

ECC Memory

Error-Correcting Code (ECC) DIMMs can detect and correct single-bit errors. Problems:

  • ECC corrects 1 flip per 64-bit word — multi-bit flips bypass it
  • ECCploit (2019) showed that an attacker can flip bits, observe the correction, and use the ECC behavior as a side channel to reverse-engineer memory contents
  • ECC doesn't prevent flips — it patches them after the fact

Increased Refresh Rate

Refreshing more often (e.g., 32ms instead of 64ms) reduces the vulnerable window. Problems:

  • Refresh burns bandwidth and power — up to 25% performance degradation
  • Still doesn't help if the attacker hammers faster than the refresh rate
  • Diminishing returns as geometry shrinks further

Software Mitigations

LPDDR4/5 introduced per-row activation counters, and operating systems have experimented with guard rows (leaving empty rows between sensitive data) and CLFLUSH restrictions. But:

  • Cache eviction attacks (like Rowhammer.js) don't need clflush
  • Guard rows waste half your DRAM capacity
  • Activation counters have limited resolution and can be overflowed

06 // THE BIGGER PICTURE

Rowhammer is part of a broader class of attacks that exploit the gap between hardware abstractions and physical reality:

  • Spectre / Meltdown — CPUs speculatively execute past security boundaries
  • Cold Boot Attacks — DRAM retains data after power-off (remanence)
  • Power Analysis — cryptographic keys leak through power consumption patterns
  • EM Emanation — electromagnetic radiation from circuits leaks information

The common theme: the hardware does not behave the way the software model assumes. Security architectures built on incorrect physical assumptions are castles on sand.

"We trust that a memory read only affects the addressed location. We trust that charge stays in capacitors between refreshes. We trust that isolation means isolation. Rowhammer proves that trust is misplaced — and that your for-loop can rewrite the kernel."

07 // THE STATE OF PLAY (2026)

Current status:

  • DDR5 — includes per-row activation counters (PRAC) and refresh management. Early results show improvement, but researchers are already finding bypass patterns.
  • Apple M-series — LPDDR5 in Apple Silicon has shown resilience, but no formal proof of immunity exists. AUGURY (speculative prefetch attack) shows ARM isn't invulnerable.
  • Cloud providers — AWS, Google Cloud, and Azure use ECC memory and TRR, but multi-tenant environments remain theoretically vulnerable to cross-VM Rowhammer.
  • Research direction — formal verification of DRAM controllers, DRAM PUFs (physically unclonable functions) for integrity checking, and complete redesigns of the DRAM refresh architecture.

The uncomfortable truth: Rowhammer cannot be fully solved without fundamentally redesigning DRAM. Every mitigation is a patch on a physical vulnerability. The question is not "will Rowhammer be exploited?" but "how many times has it been exploited already without detection?"
